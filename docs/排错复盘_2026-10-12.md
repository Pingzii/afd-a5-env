# 问题 1：`.view` 崩在 ACLGraph 捕获阶段

### 现象

```
RuntimeError: view size is not compatible with input tensor's size and stride
(at least one dimension spans across two contiguous subspaces).
Use .reshape(...) instead.
```
栈指向 `vllm_ascend/attention/dsa_attn_kv_plan.py:121`：
```python
kv_compress_cache=cache.view(-1, 1, cache.shape[-1])
```
发生在 `capture_model`（ACLGraph 捕获）阶段。**这是最早出现的、也是挡在最外面的那个错。**

### 怎么排查的

```
① 读栈 → 定位到 dsa_attn_kv_plan.py（当时是新文件），知道这是
   "选哪条 KV 压缩路径"的地方

② 判断：paged cache 是 block-strided 的，而 .view 要求连续内存
   → 结论：不该在这里 .view

③ 去读算子的 binding（csrc/torch_binding.cpp 的 kv_compress_epilog 段）
   → 看到它接受 4-D [blockNum, blockSize, 1, headDim]，并且
     IgnoreContiguous、自带 block_stride 属性
   → 强化了 ② 的判断："传 4-D 才对，不该 flatten"

④ 写 patch：把 cache.view(-1,1,C) 改成直接传 cache
   → 服务起来了 ✓

⑤ 但输出是词沙拉（→ 见问题 4）
```

**补充**：中途为了绕开这个崩溃，还试过 `--kv-cache-dtype bfloat16`（想走 BF16 路径），
撞上 `sparse_flash_mla` 未编入 ascend950（→ 见问题 7）。

### 结果：**错**

patch 让 `block_stride` 从 640 变成 20480（×32），KV 写到错误的地址 → 输出垃圾。

### 真实原因

**`.view` 崩溃是症状，不是病因。**

- 没加 fp8 flag 时，`cache_dtype="auto"` 被解析成 bf16 → cache 是非连续的
- 加上 `--kv-cache-dtype fp8` 之后，cache 变成连续的 → **`.view` 根本不崩，原始代码就能过**

```
实测证据：
  没加 flag： shape=(99686, 32, 1, 512)   stride=(20480, 512, 512, 1)   contiguous=False
  加了 flag： shape=(170574, 32, 1, 640)  stride=(20480, 640, 640, 1)   contiguous=True
```

**我改了一处本来不需要改的代码。**

### 归因：🧠 **推理问题（纯的）**

```
报错信息：给全了 —— 完整的栈、文件名、行号、错误类型，还有 Python 官方的修复建议
环境：    给全了 —— 能复现、能改、能重跑
```

**错在：看到 `.view` 崩就去修 `.view`，没有问「这个 cache 为什么是非连续的」。**

我在**现象层**动手，而根因在**契约层**（这个 cache 应该是什么 dtype、谁决定的）。

### 经验

- **报错点是「第一个发现不一致的地方」，不是出错的地方**
- **改「调用方式」之前，先问「这个契约是谁定义的」**
- 如果我当时先查一句「这个 cache 的 dtype 从哪来」，10 分钟就能到根因

# 问题 2：算子断言 cache 的 dtype 不对

### 现象

```
kv_compress_cache must be FP8_E5M2 or FP8_E4M3, but got c10::BFloat16
```
（出现在加了问题 1 的 patch 之后）

### 怎么排查的

```
① 看断言 → 是 csrc 里 validate_kv_compress_epilog_inputs 的 TORCH_CHECK
② 判断：cache 得是 FP8
③ 试 --kv-cache-dtype fp8
   → 这个错消失了 ✓
   → 但立刻暴露出下一个错（问题 3）
```

### 结果：**对了一半**

- 加 fp8 flag 确实解决了这个错 ✓
- **但我把它当成「绕过手段」，没意识到它是「契约的直接陈述」** ✗

### 真实原因

**这条报错信息其实就是根因的翻译：**

```
我说的是："cache 得是 FP8，那就加个 flag"
该说的是："cache 应该是 FP8，但实际是 BF16 —— 
            那么是谁、在哪一步决定了它是 BF16？"
```

**问题 1 和问题 2 是同一个根因的两个表现**（`cache_dtype` 被解析成 bf16）。
如果我从问题 2 往上游追一步，就能同时解决两个 —— 也就不需要问题 1 那个错 patch 了。

### 归因：🧠 **推理问题**

信息完全够：**报错本身就写着契约和实际值的对比。**

### 经验

- **算子的断言往往直接告诉你契约是什么** —— 「应该是 X 但是 Y」，要去问「Y 是谁给的」
- 同一个根因会有多个表现；**找到能同时解释多个现象的假设，比逐个修现象划算**

# 问题 3：indexer 的 tiling 校验失败

### 现象

```
aclnnIndexerCompressEpilogV2 failed (EZ1008) ...
block_stride must be greater than min block size 8448.
[FUNC:CheckShapesAndAttrs][FILE:indexer_compress_epilog_v2_tiling.cpp][LINE:136]
```

### 怎么排查的（这一段有曲折，值得细写）

```
① 读 tiling 源码（csrc/.../indexer_compress_epilog_v2_tiling.cpp:132-144）
   → int64_t minBlockSize = cacheBs_ * cacheD_;
   → 要求 blockStride_ >= minBlockSize
   → 但不知道 cacheBs_ / cacheD_ 的实际值（它们来自传进来的张量）

② 读 binding（torch_binding.cpp:1835-1844）
   → indexer_compress_cache_stride = indexer_compress_cache.stride(0)

③ ★ 我让用户加诊断补丁，在 device_op.py 调算子之前打印张量几何

④ 用户跑了，输出：
   AFD-PROBE indexer cache_shape=(170574, 32, 1, 132)
             cache_stride=(4160, 132, 132, 1)
             cache_dtype=torch.bfloat16 cache_contig=False
             tiling_min_block_size=4224
             binding_block_stride=4160
             k_cache_shape=(170574, 32, 1, 128)
             x_shape=(256, 128) slot_shape=(256,)

⑤ ★★ 用户质疑："你这个真的 print 了吗？"
   → 我复查发现：我算出的 min_block_size 和 block_stride 是在
     .view(torch.uint8) 【之前】算的，而算子实际拿到的是之后的张量
     → 两个派生值都差了 2 倍
   → 结论不变（两边同比例缩放），但过程必须认

⑥ 用算术证伪：
       spec 分配的页面大小：32 × (128×2 + 1×4) = 8320 字节/block → 每行 260 字节
       shape 隐含的：      last_dim = 128 + 1×4 = 132 → 当成 132 个【元素】
                          132 × 2 字节 = 264 字节/行
       差额 4 字节 → 指向「132 把 4 个【字节】当成了 4 个【元素】」
       → 只在 K 是 1 字节时自洽

⑦ 顺着 dtype 追到 worker/v2/attn_utils.py:123
   → c8_k_cache_dtype = kv_cache_dtype_str_to_dtype(indexer_kv_dtype, model_config)
   → 而该字段默认 "auto" → 解析成 bf16

⑧ 去 vLLM 源码查这个字段该解析成什么
   → vllm/config/attention.py:83-87 的 docstring：
       """... "auto" picks the model's default
          (bf16 for MiniMax M3, fp8 for the DeepSeek sparse indexer). ..."""
   → ★ 文档明说 DeepSeek 稀疏 indexer 的 auto 就该是 fp8
   → 而 upstream 的 DSA backend 确实调用 resolve_indexer_kv_dtype("fp8")
   → vllm-ascend 没调用它，拿模型 dtype 去解析了 —— 契约违反，定案
```

### 结果：**最终结论对，但过程有错**

- 根因判断正确 ✓
- 中间两个派生值算错（在错误的时机算）✗ —— 被用户抓到

### 归因

```
🧠 推理问题（局部）：
   派生值算错了 —— 我在 .view(torch.uint8) 之前算，
   而算子拿到的是之后的张量（最后一维字节数翻倍）
   → 这是"没验证中间量"的问题

🖥 环境问题（但不是借口）：
   我这边没有 NPU、没有 vllm-ascend 运行时，
   打探针必须让用户跑 → 一轮往返
   
   但★这个约束不该导向"推理补缺口"，而应该导向
   "提一个最小、最便宜、结论明确的检查"
   —— 而那个探针确实是用户催我才去打的（"你这个真的 print 了吗？"）

📄 报错信息：给全了，但★这类错误的信息【本质上不可能给够】——
   tiling 报的是"block_stride 太小"，真正的问题是 dtype 让形状公式不自洽。
   报错点离根因太远，再全的报错也不够。
```

### 经验

- **探针要打在算子调用之前**，字段要含 `shape` / `stride` / `dtype` / `contiguous`
- **派生值也要验** —— 我算了两个数，两个都在错误的时机算的
- **形状和分配对不上时，两边都算成字节，差额会指向具体的公式项**

### 结果：**我的候选列表里有正确答案，但我把它排在后面**

### 归因：🧠 **推理问题，而且是方法论层面的**

```
这是最基本的变量隔离：刚改过什么，就怀疑什么。
```

### 经验

- **出问题先看"我最近改了什么"** —— 二分法的第一刀

# 问题 7：`--kv-cache-dtype bfloat16` 的弯路

### 现象

为了绕开问题 1 的 `.view` 崩溃，我推荐改走 BF16 路径。

### 怎么排查的

```
① 判断：既然非连续导致 .view 崩，那就让 cache 用 bf16（连续）
② 试 → 撞上：
     aclnnSparseFlashMla failed (EZ1009) ... SoC version ascend950 verification failed
③ 去查算子清单：
     csrc/build_aclnn.sh 的 ascend950 分支里【没有】sparse_flash_mla
     （910b / 910_93 分支里都有）
④ 让用户在绿区实测 _cann_ops_custom：
     sparse_flash_mla → 空
     kv_compress_epilog → 有
⑤ 结论：A5 上 BF16 那条路根本没有实现，只能走 FP8
```

### 结果：**我这个建议是错的，但这次错得有价值**

**它排除了整条 BF16 路径** —— 后面所有推理（"A5 只有 FP8 一条路"）都建立在这个结论上。

### 归因：📄 **信息问题 —— 但应对方式是错的**

```
我当时不知道 ascend950 编译了哪些算子。
★ 但这是【查得到】的：build_aclnn.sh 就在仓里，绿区的 _cann_ops_custom 也能 find

→ 正确的应对是"去查"，不是"试一下看会不会崩"
→ 而且这一步最后还是靠"去查"解决的
```

### 经验

- **"环境里有什么"也是可以查的元数据** —— 不必用实验去试
- 这条其实是**方法论第 4 条**（查证分层：最便宜的一层是"存在吗"）的一个实例

# 归纳成一句话

```
8 个问题里 7 个是"想错了"，不是"不知道"。

共同模式：我在【现象层】和【实现层】用力，
         却跳过了最便宜的【元数据层】。
```

**具体表现：**

```
本该先做（便宜、本地就有）：
    git grep   → 存在吗？在哪？几处？
    git diff --stat → 哪个文件是新增的？
    git log    → 什么时候变的？
    查文档/docstring → 契约是什么？

我实际先做（贵、且不可靠）：
    读算子 tiling 源码 → 推公式 → 写 patch → 让绿区跑 → 输出错了 → 再来一轮
```

**顺序反了，代价是一整轮 + 一个把 `block_stride` 放大 32 倍的错补丁。**
