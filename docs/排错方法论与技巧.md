# 排错的方法论与技巧

> 从 2026 年 9 月的 AFD Graph 算子异常定位，以及 2026-10-12 的排错中提炼。
> 方法论只留可迁移的思维原则；技巧只留反复用得到的操作。

## 一、方法论

### 1. 分清错误暴露点、设备首错点和缺陷产生点

异步系统里，这三个位置可能相距很远：

```text
错误暴露点：Python traceback 中检查到设备错误的位置
设备首错点：设备上首先失败的 kernel
缺陷产生点：最早破坏数据或执行契约的位置
```

此前 DynamicMxQuant、Swiglu、record_event 都暴露过异常，但 plog 指向的设备首错是 Hash router。找到 Hash kernel 后，还要继续查是谁生成、传输或改变了错误输入。

报错位置只能说明这里发现了不一致，责任要靠契约判断：

```text
这里要求什么？
实际拿到了什么？
谁生成或改变了它？
```

契约包括 shape、dtype、stride、值域、有效长度、布局、执行顺序和 buffer 生命周期。消费端也可能实现错误，不能预先认定责任一定在上游。

### 2. 先找最小报错情况，再选择查证方向

固定版本、配置和输入，列出最接近的正常组与失败组，逐步去掉不必要条件。单请求能复现，就不带并发；更小的 topology 或 batch 能复现，就先用更小的。

| 故障差异 | 能排除什么 | 指向哪些代码 |
|---|---|---|
| 2A2F 正常，4A2F/6A2F 异常 | A>F 是必要条件之一 | 多 peer、rank 映射、聚合、分片、padding |
| eager 正常，Graph 异常 | Graph 是必要条件之一 | capture/replay、Graph key、host metadata、buffer 生命周期 |
| Graph size 8 正常，16 及以上异常 | 存在 size 边界 | bucket、对齐、有效行数和读写边界 |
| 单请求也复现 | 并发压力不是必要条件 | 数据契约和确定性执行路径 |

这些差异是源码搜索词，也是设计对照实验的依据，但不能单独证明根因。例如 Graph-only 不能直接证明读取了未初始化内存，A>F-only 也不能直接排除算子缺陷。

### 3. 用控制变量和组件交叉验证缩小范围

完整失败路径可以先抽象成：

```text
C：公共环境和基础路径
A：特性 A，例如 DeepSeek-V4 新增的模型或 Hash 路由
B：特性 B，例如 A2E/E2A 或 AFD 通信
失败现场：C + A + B
```

构造两个对照：

```text
C + A：保留模型特性，去掉或替换通信特性
C + B：保留通信特性，换成不包含新增模型特性的模型
```

判读方式：

| C+A | C+B | C+A+B | 说明 |
|---|---|---|---|
| 正常 | 正常 | 异常 | 优先查 A 与 B 的交互契约 |
| 异常 | 正常 | 异常 | A 或 A 相关路径可以独立触发 |
| 正常 | 异常 | 异常 | B 或 B 相关路径可以独立触发 |
| 异常 | 异常 | 异常 | 查公共路径 C，或检查 A、B 是否各有问题 |

此前同事建议：

- 在 A5 上测试 DPSV2：保留 A5 与 AFD/A2E 路径，去掉 DSV4 新增路径。
- 在 A3 上测试 DPV4：保留 DSV4 模型路径，改变 A5 上的通信路径。

这是一种组件交叉验证。它未必是严格的单变量实验，因为硬件、CANN、torch_npu、算子版本和配置可能一起变化。实验前要列出实际变化的所有变量；结果先用于缩小方向，再用更严格的对照确认。

每次实验都要回答：

```text
本次只想验证哪个差异？
除了目标变量，还有哪些变量同时变化？
不同结果分别支持或排除什么？
```

### 4. 新症状出现后，优先检查最近变更

如果一个新症状紧跟着 patch、配置、依赖版本、启动参数或模型文件的变化出现，第一刀先切最近变更：

```text
只撤销最近变更
→ 保持版本、配置、输入和运行方式不变
→ 重跑最小复现
→ 必要时重新应用该变更，再复现一次
```

这是成本最低、先验概率最高的一组对照。此前服务启动成功却输出“词沙拉”时，应该先怀疑五分钟前改过的 patch，而不是先考古长期未改、此前正常的 ACLGraph 和 AFD 数据面。

“先怀疑最近变更”不是认定它必然有错。撤销后症状消失，说明该变更是触发条件之一；重新应用后稳定复现，证据才更强。撤销后仍然存在，再继续检查其他模块。

不要一次撤销多项变更，否则无法知道是哪一项起作用。原始工作树里有其他修改时，只撤本次变更，并保留可恢复路径。

### 5. 先查证，再推理；不要用推理代替仓库里的已有信息

推理便宜、看起来合理，而且错了也可能不自知。查证有成本，但能把结论绑定到具体版本和事实。

**如果一个结论能用一次查证替代，就先查证。** 推理用于连接事实、提出假设和设计下一步实验，不用于替代仓库中已经存在的信息。

查证从便宜的一层开始：

```text
最便宜    存在吗？在哪？几处？签名是什么？什么时候变的？
   ↓ 不够
          上游 issue / PR / commit 有没有做过？结论和适用版本是什么？
   ↓ 不够
          当前版本怎么实现？别处尤其是上游怎么实现？
   ↓ 不够
          规范、文档和已有记录定义了什么契约？
   ↓ 不够
最贵      跑实验，看当前环境的实际值和实际路径
```

最便宜的一层经常被跳过，因为人容易直接读实现或动手改。但“有没有、在哪、几处、什么时候变的”通常已经能排除大量可能。

这层信息通常已经物化在本地磁盘上。确认本地仓库的 branch 和 commit 后，`rg`、`git diff`、`git log -S/-G`、`git show` 都是零网络、零绿区往返的查证。三个相关仓已经 clone 在本地时，应该先查本地事实，再去推 tiling 公式、写 patch、等待绿区实验；跳过手边证据，会把一个本地查询变成一整轮远端试错。

上游 issue、PR 和提交历史往往包含症状、根因、修法和验证。先花几分钟确认别人是否做过，能避免重复劳动。找到后仍要核对当前基线、依赖提交和适用条件。

### 6. 测试结论不能超过测试覆盖范围

此前 A2E payload 的均匀构造通过，只能证明均匀构造通过。它没有覆盖多 Attention peer、不均匀 per-peer count、逐步变化和 Graph replay，因此不能排除生产场景中的 A2E 问题。

每次实验都写清楚：

```text
测试覆盖了什么？
测试没有覆盖什么？
PASS 能排除什么？
FAIL 能证明什么？
```

UT 要复制故障条件，而不只是调用同一个函数。一次 PASS 只能排除本次输入、版本和执行模式覆盖的范围。

### 7. 分开报告证据、结论和验证状态

如果不区分“观察到什么”和“因此推断什么”，别人只能选择相信或不信，无法单独检查推断。

统一按下面方式记录：

```text
事实/证据：日志、源码、运行值或实验结果是什么
推断/结论：由哪些证据得到
待验证：什么实验可以确认或推翻
适用条件：版本、配置、输入和执行模式
```

验证状态单独分类：

```text
已验证：有可复现的证据
未验证：已经实现或执行，但没有检查结果
已验证但前提已变：验证后又改变了依赖版本、配置或路径
```

把未验证写成已完成，会污染后面所有基于它的判断。提交信息和进展记录只能写真实做过的验证。

## 二、技巧

### 1. 改动怎么传进绿区

前提：绿区可以 fetch、修改本地文件和执行实验，但不能 push 或 upload。

```text
改 vllm-ascend 等绿区不能直接访问或不能提交的仓
    → 蓝区生成 .patch
    → 放入本项目私仓
    → 绿区 fetch 项目仓并 git apply

改 afd-plugin 等绿区可以访问的私仓
    → 蓝区修改并 push 到对应私仓分支
    → 绿区 git fetch
    → checkout/cherry-pick 对应分支或提交
```

分界线是目标仓库在绿区能否访问，以及是否允许直接拉取该仓的提交。每个项目使用自己的工作私仓，保存环境版本、脚本、规范、patch、踩坑记录和当前进展，不要求所有项目共用一个 patchstack。

绿区实验前记录基线和已有修改，实验后只撤销本次变更，不能从绿区向外提交结果或代码。

### 2. 从 plog 找设备首错

先在下发者进程的 plog 中找当前复现最早的 fault：

```bash
rg -n -i 'fault kernel_name|kernel_name|stream_id|task_id|vector core|aivec|MTE' plog-*.log
```

用时间、PID、device、stream_id 和 task_id 关联事件，确认失败 kernel 由哪个进程、哪个角色下发。其他进程可能只在后续同步时感知到同一个设备错误。

Python traceback 用来找错误暴露位置；plog 的首错 kernel 用来确定下一步检查哪个算子；找到 kernel 后仍要沿输入来源继续回溯。

### 3. 在边界检查数据，再构造隔离测试

先按算子契约检查真实输入：

```text
shape、dtype、stride
实际有效长度
取值范围
scale 的 shape 和布局
producer/receiver/consumer 的行数
capture 与 replay 的尺寸、offset 和生命周期
```

再使用满足接口契约的输入构造算子 UT：

- 合法输入 UT 也失败：继续检查算子、tiling 和 Graph 适配。
- 合法输入 UT 通过，但真实输入违反契约：继续沿框架生产、传输和重排路径回溯。
- UT 通过且真实输入看似合法：检查 UT 没覆盖的 topology、stream、地址布局和生命周期。

此前 Hash 路由至少要检查：

```text
sender payload rows == receiver expected rows
input_ids 覆盖行数 == router 消费行数
0 <= input_ids < tid2eid 行数
消费前是否再次切分或重排
capture/replay 是否使用了不同的有效尺寸
```

隔离测试必须覆盖最小故障条件。均匀计数通过，不能代表不均匀多 peer 场景通过。

## 附：代价与教训

| 实际经历 | 应留下的习惯 |
|---|---|
| 被 DynamicMxQuant 等异步报错位置带偏 | 先找设备首错，再查输入来源 |
| A2E 理想构造 PASS，却没覆盖多 peer 动态计数 | 明确测试的排除范围 |
| 先改 InferShape、尝试替换 Hash 算子，未证实根因 | 先写契约和判别实验，核对替代接口语义 |
| 最近的补丁让服务起来了，输出却变成“词沙拉” | 新症状优先撤销最近变更，并用撤销/重放做对照 |
| 前提已变化，仍沿旧推理继续 | 结论绑定版本和配置，相关变更后重验 |
| 调查后才发现上游已有相似修复 | 早查 issue、PR 和历史提交 |
| 临时探针差点留在运行树上 | 应用前准备撤销，结束后核对状态 |
| 提交说明写了未做过的验证 | 分开记录实现状态和验证状态 |
